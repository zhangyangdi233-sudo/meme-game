對象與主題：`$ARGUMENTS`。issue 與回覆用繁體中文。

**提問票**是一張自帶主持說明的 issue：回答的人把它交給自己的 AI，AI 依票內說明一輪一輪和他討論，結束後用 `gh issue comment` 回覆結論。票要讓一個沒參與過這段對話的 AI 也能獨立主持。

## 流程

1. **定範圍**：確認誰回答、要定哪些事。只收回答者有權決定的問題；程式端自己能決定的工程問題，寫成「程式端的決定（供知悉）」或不放。不清楚就問使用者。
2. **查證**：每題的前因都要有出處：程式碼、commit、分支、文件、既有 issue 與問答紀錄（例如 `docs/design/aphasia_planner_qa.md`）。已經定案的問題拿掉，列進「已定案」。和既有 `needs-info` 票重疊的問題併進來。完成標準：每題都能指出「現況是什麼、從哪裡看到的」。
3. **排題目**：把決定畫成設計樹，依影響範圍排序，再依相依關係分輪：某題的前提要等另一題的答案，就放到後一輪。每輪 3～5 題。
4. **給使用者確認**：列出每題的標題、方案與建議，以及分輪方式。使用者同意後才開票。
5. **開票**：依下方「票的結構」寫內文，標題用 `【需要<回答者>回答】<主題>`，加 `needs-info` 標籤，用 `gh issue create --body-file` 建立。併入的舊票各留一則言，指向新票的題號。
6. **交接**：給使用者一段可以直接轉傳的訊息，內含要貼給 AI 的指令：

   > 請用 `gh issue view <N> --repo <owner/repo>` 打開 issue #N，照裡面「給 AI」那一段的說明，和我一輪一輪討論。

   並說明：AI 要能執行 `gh`，且登入有留言權限的帳號；做不到時，請回答者自己把結論貼回 issue。結論只會以留言出現，標籤由程式端讀完再改。

## 票的結構

依序包含：

1. **為什麼有這張票**：兩三句說明背景，加一個最具體的例子（時間線或前後對照最有效）。
2. **已定案**：一行列完，避免重問。
3. **怎麼回答**：同意建議就回「同意」，有其他想法直接說。
4. **給 AI 的主持說明**：照下面的範本，換掉輪次、題號與資料位置。
5. **題目**：每題用 grilling 格式。

```
❓ **Qn - <標題>**：<前因：現況與出處> <後果：為什麼這題會影響後面>
- (a) …
- (b) …
- (c) …

➡️ <程式端建議>。<一句理由>
```

### 給 AI 的主持說明（範本）

```
## 給 AI：請用這份 issue 和<回答者>進行討論

<回答者>會請你打開這個 issue。請你主持這場討論，不要只做摘要：

1. **分輪進行，每輪問完再等<回答者>回答。** 前面的答案可能改變後面的題目。
   - 第 1 輪：Q1、Q2…
   - 第 2 輪：…（依第 1 輪結果調整後再問）
2. **每題沿用下面的格式**：`❓ Qn - 標題：前因後果`，列出方案，最後是 `➡️ 程式端建議`。用白話說明，讓<回答者>一回「同意」就能往下走。
3. **<回答者>選了不同方案或提出新想法時**，說明這個選擇對其他題目的影響，必要時調整後面的題目或補問。決定權在<回答者>。
4. **需要查資料時自己查。** <列出原始文件、分支、現況整理的位置>
5. **全部討論完後**，先把結論給<回答者>確認，再用 `gh issue comment <N>` 留言回覆。每題一行：題號、選擇的方案、一句原因；沒定的寫「未定」和卡住的地方。這份 issue 沒涵蓋的新想法，另外列在最後。
```

## 寫法

- **平輩協作的語氣**：回答者是一起做遊戲的夥伴。用白話直接講現況和取捨。
- **從整個專案的角度提問**：先問會決定骨架的事（核心體驗、核心循環、各部分的定位、範圍），細節題放後面。
- **每題 2～4 個方案**，各方案寫出會帶來什麼結果；建議要明確選一個。
- 答案格式交給 AI 整理。票內只放題目、建議與主持說明。

## 回收

使用者說對方回覆了，就讀 `gh issue view <N> --comments`，逐題對照結論，列出「已定」「未定」「新想法」，再和使用者決定要改哪些票、開哪些新票；全部處理完才移除 `needs-info` 或關票。
