## 流程

1. **定位**：先看全局：讀 `CONTEXT.md`，用 `gh issue list --state open` 看未完成的票，並讀這張票依賴或會解鎖的票。沒給票號（`$ARGUMENTS` 為空）時，從 `ready-for-agent` 的票裡挑依賴都已完成、最能推進可玩 demo 的一張。完成標準：能說出這張票在整個專案裡接在什麼之後、解開了什麼。
2. **開工前說明**：動手前先告訴使用者要做哪一張票，寫成一小段：
   - 票號、標題與一句話講它要讓遊戲多出什麼。
   - 為什麼是這張：接在哪張之後、依賴是否都已完成；若是自己挑的，說明挑它而不挑其他票的理由。
   - 預計會動到哪些系統，以及有沒有需要企劃先拍板的疑點。有疑點就停下來問，沒有就直接進下一步。
3. **實作到關票**：讀 `.claude/skills/implement-ticket/SKILL.md`，以步驟 1 確定的票號照做。
4. **說明**：用整個專案的視角告訴使用者，遊戲現在有什麼不同。假設讀者是一起做遊戲、沒看過程式碼的夥伴，以玩家走過的流程與系統之間的關係來講，檔案名稱只在需要追查時才出現：
   - **這張票在專案裡的位置**：它屬於專案的哪一塊，為什麼現在做。
   - **遊戲現在有什麼不同**：玩家實際會遇到的前後對照，從哪裡開始、會看到什麼、結果如何。玩家看不到的改動，就寫它讓後續哪件事變得可行。
   - **對其他部分的影響**：哪些既有系統或內容因此改變了行為，內容與美術製作要配合什麼。
   - **離目標還差多少**：這張票解鎖了哪些票，走到能玩的 demo 還缺哪幾張。
   - **驗證到哪裡**：哪些有自動測試佐證，哪些要人實際進遊戲試玩才算數。
   - **遺留事項**：沒採納的審查建議，與留給後續票的事項，各附一句對專案的影響。
5. **下一張票**：關票後重新跑一次 `gh issue list --state open`，推薦接下來做哪一張：票號、標題、為什麼是它（依賴剛被解開、或最接近可玩 demo），以及它開工前需不需要企劃先回答問題。若有兩張以上同樣合理，列出候選並說明取捨，給一個推薦。不要自己接著開工。
